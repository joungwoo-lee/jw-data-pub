Claude Code Skills · 실전 설계

Skill은 프롬프트가 아니라
“일하는 방식”이다

반복 업무를 Claude에게 맡길 때, 매번 장문의 지시를 다시 쓰는 대신 언제 무엇을 보고, 어떻게 판단하고, 어디까지 하면 끝인지를 재사용 가능한 SOP로 만듭니다.

판단 기준작업 절차참고자료스크립트완료 조건
핵심: “똑똑하게 해줘”가 아니라 “우리 팀은 이렇게 일한다”를 가르친다.
01 · 먼저 이것만

CLAUDE.md와 Skill은 역할이 다르다

항상 적용
CLAUDE.md = 헌법

프로젝트에서 늘 지켜야 하는 기본 규칙입니다.

• 답변은 한국어
• 기존 정보 임의 삭제 금지
• 수정 전 기존 구조 확인
필요할 때 적용
Skill = 업무 SOP

특정 종류의 일이 들어왔을 때 꺼내 쓰는 작업법입니다.

• 뉴스 조사
• 팩트체크
• 보고서 편집
• 배포
항상 필요한 규칙은 CLAUDE.md, 특정 업무의 노하우는 Skill.
02 · 기본 구조

SKILL.md는 지휘서다

my-project/
├─ CLAUDE.md
└─ .claude/skills/
   └─ news-research/
      ├─ SKILL.md
      ├─ references/
      │  └─ source-policy.md
      └─ scripts/
         └─ validate.py

세 덩어리로 생각하면 쉽습니다.

SKILL.md — 무엇을 어떤 순서로 할지

references/ — 필요할 때 읽을 교과서·사내 규칙

scripts/ — 계산·검증처럼 확실해야 하는 기계적 작업

SKILL.md 안에 세상 모든 정보를 넣는 것이 목적이 아니다.
03 · 첫 번째 꿀팁

만능 Skill 하나를 만들지 마라

나쁜 구조
super-skill

조사 → 계산 → 작성 → 검증 → HTML 수정 → 배포까지 전부 한 Skill.

길어지고, 수정하기 어렵고, 필요 없는 지시까지 계속 끌고 다닙니다.

좋은 구조
research
fact-check
report-edit
critic
publish

작은 전문가를 필요에 따라 조합합니다.

Skill의 좋은 크기 = “하나의 명확한 책임”.
04 · 자동 호출의 핵심

description은 설명문이 아니라 라우팅 규칙

애매함
description: 뉴스를 조사한다.

Claude 입장에서는 언제 이 Skill을 꺼내야 할지 애매합니다.

구체적
description: >
  AI·반도체·빅테크 뉴스를
  조사하거나, 기사 속 숫자와
  기업 발표를 교차검증할 때 사용한다.

무엇을 하는지 + 언제 쓰는지를 같이 적습니다.

좋은 description은 Skill의 검색 키워드이자 호출 조건이다.
05 · 컨텍스트 절약

필요한 자료만 그때 읽게 한다

Progressive Disclosure

회계 규칙, 산업 지식, 스타일 가이드를 SKILL.md에 전부 복붙하지 않습니다.

작업에 필요한 자료만 references에서 읽게 합니다.

financial-analysis/
├─ SKILL.md
└─ references/
   ├─ accounting.md
   ├─ semiconductor.md
   └─ valuation.md

반도체 분석이면
→ semiconductor.md 읽기
SKILL.md = 지휘서 / references = 교과서. 둘을 섞지 않는다.
06 · Claude와 코드의 역할

생각은 Claude, 확실해야 하는 것은 Script

Claude가 잘하는 것

판단 · 해석 · 요약

문맥을 읽고 애매한 상황에서 의미를 판단하는 일.

Script가 잘하는 것

계산 · 검증 · 반복

같은 입력이면 같은 결과가 나와야 하는 일.

예: 영업이익률 계산을 매번 모델에게 암산시키기보다 계산 스크립트를 둡니다.

LLM에게 모든 것을 시키는 것이 에이전트 설계가 아니다.
07 · 완료의 정의

“잘 해줘” 대신 끝나는 조건을 준다

왜?

Claude가 스스로 “이 정도면 됐겠지”라고 종료하는 기준은 내가 원하는 기준과 다를 수 있습니다.

## 완료 조건
- [ ] 기사 날짜 확인
- [ ] 핵심 숫자 원문 확인
- [ ] 중요 주장 교차검증
- [ ] 사실과 추론 구분
- [ ] 기존 중요 정보 보존
- [ ] 미해결 충돌 없음
Definition of Done을 Skill에 넣으면 결과의 편차가 줄어든다.
08 · 심화 핵심

지식을 넣기보다 판단 기준을 넣어라

“정확하게 조사해”는 약한 지시입니다.

대신 충돌할 때 무엇을 믿을지 정합니다.

정보가 충돌하면:
1. 기업·기관 공식 원문
2. 규제기관 자료
3. 직접 취재한 신뢰 매체
4. 전문 매체
5. 2차 인용

숫자가 다르면 임의 선택 금지.
차이를 명시한다.
좋은 Skill은 지식 창고보다 “판단 정책”에 가깝다.
09 · 절차보다 강한 것

작업 순서만 말하지 말고 분기를 설계

새로운 사실인가?
 ├─ YES → 출처 확보
 │          ↓
 │       핵심 주장인가?
 │        ├─ YES → 교차검증
 │        └─ NO  → 신뢰 출처 1개 허용
 └─ NO → 기존 자료 유지

숫자인가? → 단위·기간·통화 확인
추론인가? → 사실과 분리해서 표시

현실의 업무는 항상 같은 직선 경로로 흘러가지 않습니다. 상황별 행동을 알려줘야 예상 밖 입력에도 강합니다.

SOP를 체크리스트가 아니라 작은 의사결정 트리로 만든다.
10 · 지시문 작성법

“하지 마”에서 끝내지 말고
대신 무엇을 할지 말한다

약한 지시
내용을 삭제하지 마라.

삭제가 필요한 예외 상황에서 행동 방법이 없습니다.

강한 지시

기존 내용을 보존하고 필요한 부분만 수정.

삭제가 필요하면 삭제 대상과 이유를 먼저 확인한다.

금지 규칙 + 대체 행동을 함께 준다.
11 · 작성자와 감사자를 분리

검증 Skill은 따로 둬라

research→write→critic→fact-check

왜 분리?

작성한 모델에게 “네 글 잘 썼는지 봐”라고 하면 자신의 논리를 그대로 옹호하기 쉽습니다.

# critic
작성자의 의도를 옹호하지 않는다.
오류를 찾는 것이 목적이다.

- 숫자 오류
- 날짜 오류
- 인과관계 비약
- 근거 없는 주장
- 빠진 반론
작성자와 감사자의 목표를 일부러 다르게 만든다.
12 · 환각 줄이는 구조

증거 → 주장 순서를 강제

위험
결론 먼저

“AI 투자가 버블이다” → 그 결론을 뒷받침할 자료를 찾아 붙이기.

권장
증거 먼저

Sources → Evidence table → Claims → Interpretation → Final.

중간 evidence table은 사용자에게 꼭 보여줄 필요가 없습니다. 작업 순서만 그렇게 강제해도 효과가 큽니다.

결론에 증거를 끼워 맞추지 말고, 증거에서 결론을 만든다.
13 · 긴 작업의 비밀

컨텍스트만 믿지 말고 파일을 작업 메모리로

.work/
├─ sources.md
├─ claims.md
├─ conflicts.md
├─ todo.md
└─ verification.md

30~60분짜리 작업이라면?

앞에서 확인한 숫자, 미해결 문제, 다음 단계가 대화 컨텍스트 속에만 있으면 놓치기 쉽습니다.

상태를 파일로 외부화하면 중간에 길어져도 다시 읽고 이어갈 수 있습니다.

컨텍스트 = RAM, 작업 파일 = 디스크라고 생각하면 쉽다.
14 · 재실행 안전성

같은 Skill을 두 번 돌려도
망가지지 않게

문제
면책문구를
문서 마지막에 추가한다.

두 번 실행하면 면책문구가 두 개 생길 수 있습니다.

Idempotent
면책문구를 먼저 검색한다.

있음 → 필요한 경우만 수정
없음 → 새로 삽입

몇 번 실행해도 결과가 안정적입니다.

자동화는 “한 번 잘 됨”보다 “반복해도 안전함”이 중요하다.
15 · 기존 문서 수정

최소 변경 원칙을 명시

왜 필요한가?

“이 문장만 고쳐”라고 했는데 Claude가 주변 문장까지 친절하게 정리해버리면 기존 정보가 변할 수 있습니다.

## Minimal-change principle
1. 수정 대상 정확히 식별
2. 주변 의존성 확인
3. 요청 범위만 수정
4. 기존 중요 정보 보존 확인

요청받지 않은 부분은
개선하지 않는다.
편집 Skill에서는 창의성보다 변경 범위 통제가 더 중요할 때가 많다.
16 · 실패도 설계 대상

정상 경로만 쓰면 Skill이 약하다

## Failure handling

출처를 못 찾음
→ 추측하지 않는다.

출처끼리 숫자가 다름
→ conflicts.md에 기록한다.

스크립트 실패
→ 성공으로 간주하지 않는다.

테스트 실패
→ 수정 후 다시 실행한다.

배포 실패
→ 완료했다고 보고하지 않는다.
“시도했다”와 “성공했다”를 반드시 구분하게 만든다.
17 · 언제 멈출 것인가

Stop condition을 넣어라

조사 종료
  • 핵심 주장 5개 검증 완료
  • 중요 숫자 원출처 확보
  • 중요한 출처 충돌 해결

충족되면 추가 검색을 중단.

완료 금지
  • 핵심 숫자 미검증
  • 깨진 링크
  • 테스트 실패
  • 미해결 중요 충돌

하나라도 있으면 완료하지 않음.

“언제 끝내라”와 “언제 끝내면 안 된다”를 둘 다 정의한다.
18 · 예제의 질

평범한 예보다 경계 사례를 가르쳐라

원문

“plans to invest up to $100B”

잘못

“1000억 달러를 투자했다.”

올바름

“최대 1000억 달러 투자 계획을 밝혔다.”

계획 / 약속 / 계약 / 집행 / 지급 완료를 구분하도록 이런 애매한 사례를 넣습니다.

Claude가 이미 잘하는 정상 사례보다, 자주 틀리는 경계 사례가 더 값지다.
19 · Skill도 소프트웨어다

Skill 자체를 회귀 테스트한다

tests/
├─ normal.md
├─ conflicting-sources.md
├─ missing-source.md
├─ ambiguous-number.md
├─ existing-content.md
└─ dangerous-edit.md

Skill을 고쳤는데 더 나빠질 수도 있습니다.

고정된 테스트 요청들을 다시 실행해 이전에는 잘하던 일을 망치지 않았는지 확인합니다.

프롬프트 감으로 튜닝하는 단계에서 한 단계 올라가는 방법입니다.

Skill도 버전업하고, 테스트하고, 실패 사례를 다시 학습시킨다.
20 · 큰 그림

Orchestrator + Specialist

report-workflow→research→fact-check→edit→critic

Orchestrator는 세부 지식을 많이 갖지 않습니다.

“먼저 조사 → 중요 주장 검증 → 문서 반영 → 감사”처럼 누구를 언제 부를지만 관리합니다. 각 Specialist는 자기 업무만 잘합니다.

큰 워크플로는 거대한 Skill이 아니라 작은 Skill들의 조합으로 만든다.
21 · 자동 호출을 막아야 할 때

위험한 작업은 사람이 직접 호출

---
name: publish-report
description: 완성된 보고서를 배포한다.
disable-model-invocation: true
---

예

/deploy
/publish
/delete
/release

외부에 영향을 주거나 되돌리기 어려운 행동은 명시적으로 실행하게 하는 편이 안전합니다.

“할 수 있음”과 “자동으로 해도 됨”은 다른 문제다.
22 · 실제 적용 예

뉴스 → 보고서 업무라면 이렇게

news-research→fact-check→report-editor→critic→publish
Research

원문·날짜·숫자 확보

Editor

기존 정보 보존 + 최소 수정

Critic

오류·비약·누락 공격적으로 검사

사용자는 “이 뉴스 조사해서 기존 보고서에 넣어”라고만 해도 된다.
23 · 가장 중요한 설계 원칙

좋은 Skill은 Claude에게
생각의 레일을 깔아준다

1

판단

무엇을 믿고 어떻게 분기할지.

2

상태

무엇을 기억하고 어디에 기록할지.

3

종료

언제 성공이고 언제 실패인지.

프롬프트를 길게 쓰는 것이 아니라 실패하기 어려운 시스템을 만든다.
24 · 한 장 요약

이렇게 기억하면 된다

CLAUDE.md = 헌법

Skill = SOP

references = 교과서

scripts = 기계적 실행

critic = 감사팀

tests = 품질보증

Claude Code를 “코딩 챗봇”이 아니라 반복 업무를 수행하는 작은 조직처럼 설계한다.
